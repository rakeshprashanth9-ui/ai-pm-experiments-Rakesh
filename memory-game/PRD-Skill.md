# PRD Skill Template

This template is a reusable guide for writing structured Product Requirement Documents (PRDs). Contributors can use it to capture the problem, scope, user needs, technical approach, and acceptance criteria in a consistent format.

## 1. Title
- Give the feature or enhancement a clear, concise name.

## 2. Purpose
- Why are we building this? Describe the primary goal and the user benefit.

## 3. Background
- What is the current context or existing behavior?
- Why is this change needed now?

## 4. Scope
- What is in scope for this work?
- What is explicitly out of scope?

## 5. User Stories
- List the main user stories for the feature.
- Example:
  - As a [user type], I want [goal] so that [reason].

## 6. Requirements
### 6.1 Functional
- Describe the behavior the system must provide.
- Include UI actions, data handling, and state changes.

### 6.2 Visual / Design
- Describe the expected UI/UX appearance.
- Specify any visual style or layout expectations.

### 6.3 Accessibility
- Describe how the feature should support keyboard navigation, screen readers, and contrast.

### 6.4 Technical
- Describe implementation details, architecture decisions, and constraints.
- Mention the files, components, or modules likely to be touched.

## 7. Acceptance Criteria
- Write clear, testable criteria.
- Use checkboxes for each outcome.
- Include behavior, visual, and accessibility criteria where applicable.

## 8. Implementation Notes
- Provide guidance for engineers on the specific changes to implement.
- Mention patterns, storage keys, class names, or APIs.

## 9. Testing
- Describe the test scenarios and validation steps.
- Include functional, visual, accessibility, and regression checks.

## 10. Success Metrics
- Define how the feature will be judged successful.
- Include user impact, quality goals, or performance targets.

---

### How to use this template
1. Duplicate this file or copy the core sections into a new PRD document.
2. Replace the generic guidance with feature-specific details.
3. Keep the structure intact for easy review and alignment.
4. Use the Acceptance Criteria section to support QA and stakeholder validation.

### Best practices
- Keep descriptions concise and actionable.
- Avoid implementation-specific details in the user stories section.
- Use measurable acceptance criteria.
- Update the document as requirements evolve to keep it accurate.
